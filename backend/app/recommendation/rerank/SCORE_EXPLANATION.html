Giải thích cách tính điểm Rerank

Tài liệu này giải thích theo kiểu mentor review được: input vào là gì, thiếu dữ liệu thì sao, mỗi feature score tính thế nào, tag nào được dùng, penalty trừ ra sao, và khi nào LLM ảnh hưởng rank.

1. Rerank Đang Làm Gì?

Rerank nhận một list khách sạn đã được search/retrieve trước đó, rồi sắp xếp lại theo mức phù hợp với user. Nó không tự tìm thêm khách sạn mới. Nếu bật PostgreSQL enrichment thì PostgreSQL chỉ bổ sung thông tin cho đúng các candidate đã truyền vào.

1Input

candidate_items, user_id, optional user_context, query, options.

2Rule Score

Hard filter trước, sau đó tính 9 feature score và trừ negative penalty.

3Final Rank

Nếu không dùng LLM: final_score = base_score. Nếu dùng LLM: merge base và LLM score.

Quan trọng: Users trong Mongo chỉ chứa long-term profile. Những field theo phiên tìm kiếm như destination, number_of_guests, session_price_range phải truyền vào request qua options.session_context.

2. Ví Dụ Input Thực Tế

Ví dụ user đang tìm khách sạn ở Vũng Tàu, đi gia đình, muốn giá 7-15 triệu, ưu tiên view hồ.

{
  "user_id": "user_002",
  "query": "Tôi đi Vũng Tàu cùng gia đình có trẻ nhỏ, muốn riêng tư, view hồ, tầm 7 đến 15 triệu",
  "candidate_items": [
    {"item_id": 1122450, "search_score": 0.90},
    {"item_id": 161729, "search_score": 0.80}
  ],
  "options": {
    "top_k": 3,
    "use_llm_rerank": false,
    "enrich_postgres_candidates": true,
    "session_context": {
      "destination": "Vũng Tàu",
      "number_of_guests": 4,
      "session_price_range": {"min": 7000000, "max": 15000000, "currency": "VND"},
      "session_trip_types": {"Gia đình có trẻ nhỏ": {"count": 8}},
      "session_hotel_types": {"Khách sạn": {"count": 10}},
      "session_room_views": {"Hướng Hồ": {"count": 10}},
      "session_amenities": {"WiFi miễn phí": {"count": 8}}
    }
  }
}

Sau normalize, các count được chuyển thành weight 0..1 trong từng group. Group nào có count cao nhất sẽ thành 1.0.

3. Thiếu Dữ Liệu Thì Sao?

Tình huống Cách xử lý Lý do
Không có session_price_range hoặc hotel thiếu giá budget_score = 0.5 Không đủ dữ liệu để nói rẻ/đắt, nên cho điểm trung tính.
Không có session amenities và long-term amenities amenity_score = 0.5 Không biết user thích tiện ích gì, không thưởng cũng không phạt.
Không có room view preference room_view_score = 0.5 Không có tín hiệu view, dùng neutral.
Không có personalization group nào source_score = 0.5 Không có hotel type/trip type/habit để match.
Không có nearby place location_score = 0.45 Neutral hơi thấp vì chưa chứng minh được gần nơi user muốn.
Không có booking gần đây trend_score = 0.0 Trend là tín hiệu thưởng thêm, không có thì không cộng.
Không có LLM hoặc LLM lỗi final_score = base_score Rule-based vẫn chạy độc lập.

4. Hard Filter Trước Khi Tính Điểm

Hard filter là cửa loại bắt buộc. Bị loại ở đây thì khách sạn không vào bảng score nữa.

Điều kiện Reason Ví dụ
Sai điểm đến destination_mismatch User tìm Vũng Tàu, hotel ở Đà Nẵng.
Hết phòng not_available available=false.
Loại khách sạn bị avoid rất mạnh strong_avoid_hotel_type User avoid Biệt thự nghỉ dưỡng với weight >= 0.85.
Tiện ích bị avoid rất mạnh strong_avoid_amenity User avoid Ban công sân hiên với weight >= 0.90.
Habit/location bị avoid rất mạnh strong_avoid_preference_habit / strong_avoid_location Candidate có đúng tín hiệu mà user negative preference đang tránh.
Giá quá xa budget price_far_outside Budget 7-15 triệu, hotel 200-360 nghìn hoặc 28-50 triệu có thể bị loại.

5. Công Thức Base Score

Sau hard filter, mỗi hotel có 9 feature score. Tất cả score đều trong khoảng 0..1.

base_score = clamp( 0.12*keyword + 0.10*budget + 0.14*amenity + 0.10*room_view + 0.10*review + 0.13*availability + 0.12*personalization + 0.09*location + 0.10*trend - negative_penalty )
Feature Weight Ý nghĩa ngắn gọn
keyword0.12Điểm search/retrieval ban đầu.
budget0.10Giá hotel có nằm trong budget session không.
amenity0.14Tiện ích hotel khớp user preference.
room_view0.10View phòng khớp user preference.
review0.10Rating và sentiment review.
availability0.13Còn nhiều phòng thì tốt hơn.
personalization0.12Khớp loại hotel, trip type, habit, click history.
location0.09Khớp nearby place user đang cần.
trend0.10Hotel đang được booking nhiều gần đây.

6. Ví Dụ Tính Từng Feature

6.1 Keyword

Nếu search trả về search_score=0.90, normalizer map sang keyword_score=0.90.

keyword = clamp(0.90) = 0.90

Nếu candidate không có điểm search:

keyword = 0.50

6.2 Budget: Đủ Giá

User muốn 7-15 triệu. Hotel giá 8-13 triệu.

  • User width = 15 - 7 = 8 triệu.
  • Overlap = 13 - 8 = 5 triệu.
  • Coverage = 5 / 8 = 0.625.
  • User center = 11 triệu, hotel center = 10.5 triệu.
  • Center score = 1 - 0.5/8 = 0.9375.
budget = 0.65*0.625 + 0.35*0.9375 = 0.734

6.3 Budget: Thiếu Giá

Nếu hotel không có price_min hoặc price_max, không thể tính overlap.

budget = 0.50

Đây là neutral, không phải điểm tốt.

6.4 Budget: Không Overlap

User muốn 7-15 triệu. Hotel giá 16-18 triệu.

  • Không overlap.
  • Khoảng cách gần nhất tới budget = 16 - 15 = 1 triệu.
  • User width = 8 triệu.
budget = clamp(1 - 1/8) = 0.875

Vì chỉ lệch nhẹ nên chưa bị phạt mạnh. Nếu lệch quá xa, hard filter có thể loại trước.

6.5 Amenity

User session muốn:

{
  "WiFi miễn phí": 1.0,
  "Bể bơi": 0.5
}

Hotel có:

["WiFi miễn phí", "Máy pha trà cà phê"]
amenity = matched_weight / total_weight = 1.0 / 1.5 = 0.667

6.6 Amenity: Session + Long-term

Nếu có cả session và long-term thì session quan trọng hơn.

amenity = 0.70*session_overlap + 0.30*long_term_overlap

Ví dụ session overlap 0.8, long-term overlap 0.4:

amenity = 0.70*0.8 + 0.30*0.4 = 0.68

6.7 Room View

Cùng cách tính với amenity, nhưng so với hotel.room_views.

User muốn Hướng Hồ, hotel có Hướng Hồ:

room_view = 1.0

User muốn Hướng Hồ, hotel chỉ có Hướng Thành phố:

room_view = 0.0

6.8 Review

Hotel rating 4.6, sentiment 0.8.

review = ((4.6 - 3.0)/2.0)*0.7 + 0.8*0.3 = 0.80

Nếu thiếu sentiment thì default sentiment là 0.5.

6.9 Availability

available_roomsScore
10 trở lên1.00
5 đến 90.85
1 đến 40.65
0 hoặc available=false0.00

6.10 Location

User muốn gần Nơi Biểu Diễn Văn Nghệ.

Hotel có nearby place đó:

location = 0.45 + 0.30 = 0.75

Hotel không có nearby place đó hoặc thiếu nearby data:

location = 0.45

7. Personalization Score Dễ Hiểu Hơn

Personalization gồm 3 nhóm match, tính riêng session và long-term:

  1. hotel_types: user thích loại khách sạn nào, hotel có đúng loại đó không.
  2. trip_types: user đi kiểu gì, hotel tag có đúng trip type đó không.
  3. preference_habits: user thích privacy/safety/quiet..., hotel có habit đó không.
source_score = average(score hotel_type, score trip_type, score preference_habit)

Sau đó:

personalization = 0.70*session_source_score + 0.30*long_term_source_score

Ví dụ đủ dữ liệu

User/session

{
  "session_hotel_types": {"Khách sạn": 1.0},
  "session_trip_types": {"Gia đình có trẻ nhỏ": 1.0},
  "session_preference_habits": {"privacy": 1.0}
}

Hotel

{
  "hotel_type": "Khách sạn",
  "tags": ["Gia đình có trẻ nhỏ"],
  "preference_habits": ["privacy", "safety"]
}

Kết quả:

source_score = (1.0 + 1.0 + 1.0) / 3 = 1.0

Ví dụ thiếu một nhóm

Nếu session không có session_preference_habits, chỉ tính 2 nhóm còn lại:

source_score = (hotel_type_score + trip_type_score) / 2

Ví dụ tag bị bỏ qua

Hotel có tag:

["family_friendly", "near_center", "nightlife"]

Những tag này không nằm trong schema trip type, nên không làm tăng trip type score.

trip_tags_used_for_score = []
Chỉ các trip type trong schema mới được dùng từ hotel.tags. Chỉ 7 preference habits trong schema mới được dùng từ hotel.preference_habits.

8. Tag Nào Được Dùng?

Hotel tags được dùng cho trip

Nhóm du khách Cặp đôi Khách du lịch một mình Gia đình có trẻ nhỏ Gia đình có thanh thiếu niên Khách đi công tác

Preference habits được score

luxury comfort quiet privacy unique safety vibrant

Nếu input lỡ có tag khác?

Tag ngoài schema bị bỏ qua khi cộng điểm positive.

Ví dụ: family_friendly, near_center, tourist_area không tăng score.

Mình không gọi chúng là blacklist nữa, vì chúng không phải vocab chính.

9. Negative Penalty

Penalty là phần trừ trực tiếp khỏi base_score. Session negative nặng hơn long-term negative.

negative_penalty = clamp( 0.70*session_penalty + 0.30*long_term_penalty, 0.0, 0.8 )

Mỗi source penalty gồm:

Negative group Multiplier Match với candidate field
avoid_hotel_types0.40hotel.hotel_type
avoid_amenities0.18hotel.amenities
avoid_preference_habits0.30hotel.preference_habits
avoid_nearby_places0.15hotel.nearby_places
avoid_locations0.25hotel.location_tags

Ví dụ penalty

Session user avoid Ban công sân hiên weight 1.0. Hotel có amenity này.

penalty_part = 0.70 * 1.0 * 0.18 = 0.126

Nếu hotel còn bị avoid hotel type weight 0.8:

penalty_part = 0.70 * 0.8 * 0.40 = 0.224

Tổng penalty các phần sẽ bị clamp tối đa 0.8.

Negative preference là field mở trong schema. Nó có thể chứa tag nghiệp vụ như nightlife, old_facility, far_from_center. Những tag này chỉ dùng để phạt/filter nếu candidate cũng có đúng tín hiệu đó.

10. Trend Score Từ Booking

Trend được tính từ booking của candidate hotels trong 7 ngày và 30 ngày gần nhất.

trend = 0.60*n7 + 0.30*ngrowth + 0.10*n30
Biến Cách tính
n7booking 7 ngày của hotel / max booking 7 ngày trong candidate set.
n30booking 30 ngày của hotel / max booking 30 ngày trong candidate set.
ngrowthgrowth của hotel / max growth trong candidate set.

Ví dụ

Trong 10 candidate, hotel A có booking 7 ngày cao nhất nên n7=1.0. Nếu nó cũng có growth cao nhất và booking 30 ngày bằng 50% max:

trend = 0.60*1.0 + 0.30*1.0 + 0.10*0.5 = 0.95

Nếu không có booking nào:

trend = 0.0

11. Ví Dụ Tính Base Score Hoàn Chỉnh

Giả sử một hotel đã qua hard filter và có feature scores:

{
  "keyword": 0.90,
  "budget": 0.734,
  "amenity": 0.667,
  "room_view": 1.00,
  "review": 0.80,
  "availability": 0.85,
  "personalization": 0.90,
  "location": 0.75,
  "trend": 0.30,
  "negative_penalty": 0.126
}
base = 0.12*0.90 + 0.10*0.734 + 0.14*0.667 + 0.10*1.00 + 0.10*0.80 + 0.13*0.85 + 0.12*0.90 + 0.09*0.75 + 0.10*0.30 - 0.126 = 0.645

Nếu không có penalty, score sẽ là 0.771. Penalty làm tụt rank rõ ràng.

12. LLM Có Ảnh Hưởng Khi Nào?

Nếu use_llm_rerank=false:

final_score = base_score

Nếu use_llm_rerank=true và LLM trả JSON hợp lệ:

final_score = 0.70*base_score + 0.30*llm_score

Ví dụ

Hotel A base 0.65, LLM score 0.90:

final = 0.70*0.65 + 0.30*0.90 = 0.725

Hotel B base 0.72, LLM score 0.60:

final = 0.70*0.72 + 0.30*0.60 = 0.684

Vậy LLM có thể đổi rank, nhưng base score vẫn chiếm phần lớn.

Nếu LLM lỗi, timeout, JSON sai, ID không thuộc candidate, hoặc score invalid thì bỏ LLM và fallback về base score.
